# ADR-0158: Status pages

Status: Accepted

Date: 2026-10-09

## Context

Synthetic monitors (ADR-0128) say whether an endpoint is reachable and SLOs (ADR-0108) say how much error
budget is left. Both live behind a login. Teams that run a service for customers or other teams want one
read-only page they can hand out: what is up, what is not, and how the last three months went.

## Decision

- **A status page is a saved selection, not a new data source.** Table `status_pages` (migration 0072, same
  `ReplacingMergeTree` tombstone shape as `alert_templates`) holds a slug, title, description, an `Enabled`
  flag and a JSON list of components. Each component is a public display name plus a reference to a
  synthetic monitor or an SLO by id. All health data is read from what those already record.
- **Publishing is explicit and Admin-only.** CRUD is `/api/status-pages` on the Admin group, and `Enabled`
  defaults to false. A disabled or deleted page answers 404 exactly like a page that never existed.
- **One unauthenticated endpoint**, `GET /api/public/status/{slug}`, mapped outside the authenticated groups
  like the alert ack link (ADR-0127). The response carries the title, description, an overall state, and per
  component the display name, state, 90-day uptime and one uptime value per UTC day. It carries no ids,
  monitor names, targets or SLO names, so a page cannot leak what it was not told to show.
- **State rules are pure** (`StatusEvaluator`). A monitor is Operational when every location that reported
  within three intervals is up, Outage when none is, Degraded when some are, and Unknown when it is disabled,
  never reported or went stale, so a stopped monitor does not stay green. An SLO is Operational while its
  error budget is unspent, Degraded once overspent and Unknown with no traffic. The page's overall state is
  the worst known component.
- **History comes from existing storage.** A monitor's days are the mean of `synthetic.up` per UTC day from
  `metrics_gauge`; an SLO's days are the good-event fraction from the hourly series `GET /api/slos/{id}/status`
  already computes, so an SLO shows at most its own window.
- **Anonymous load is bounded by a cache.** The built page is cached in memory for 30 seconds per slug, misses
  included, and served with `Cache-Control: public, max-age=30`. The build clears the caller's project scope
  (ADR-0123) so a signed-in member's narrowed counts are never cached for everyone.
- **The dashboard route `/status/{slug}`** is a public route in the root layout (no session check, no app
  chrome, `noindex`), refreshing every minute.

## Alternatives considered

- **Publish every monitor and SLO automatically.** Rejected: internal names and targets would leak, and
  publishing health data should be a deliberate act.
- **A separate static site generated by a job.** Rejected: it adds a deployment and goes stale; the cached
  endpoint is cheap.
- **Per-component public/private flags on monitors and SLOs.** Rejected: a page-level selection lets the same
  monitor appear on several pages under different names.

## Consequences

- A monitor is matched to its data by name (the `monitor` metric attribute), so renaming a monitor starts its
  history over. This is the same limit the monitors table has.
- A component whose monitor or SLO was deleted stays on the page as Unknown instead of vanishing.
- The page is visible to anyone who can reach the instance. Put the API behind your network controls if that
  is too wide; `Cors:AllowedOrigins` must still list the dashboard's origin.
- Components read ClickHouse on a cache miss: one monitor list, one status query and one daily-uptime query
  per page, plus one status query per SLO component.

## Not decided here

- **Incidents and announcements** (a status history with written updates), subscriptions, custom domains and
  branding. Each can be added without changing this shape.
- A `flare status-pages` CLI command and a Terraform resource.
