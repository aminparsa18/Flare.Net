# ADR-0044: Reset-aware increase() for Sum metric-threshold alerts

Status: Accepted

Date: 2026-09-24

## Context

ADR-0035 replaced `MetricSeriesQueryBuilder`'s Sum-type `max(Value) -
min(Value)` with a windowed, reset-aware per-row-delta `increase()`, but
deliberately left `MetricAlertConditionQueryBuilder` (ADR-0020's
metric-threshold alert evaluation) on the old expression, recording it as a
separate, named gap.

That builder produces one scalar over the whole evaluation window,
aggregated across everything the condition's `MetricFilter` matches. So
`max(Value) - min(Value)` had the same problems the chart had, and one more:

- A counter reset (process restart) mid-window read as a dip, or produced a
  wildly wrong value. An alert on "requests in the last 5 minutes > N" could
  miss or fire falsely whenever a service restarted.
- Delta-temporality points were treated as cumulative (`5, 5, 5` evaluated
  to `0`, not `15`).
- There was no per-series partitioning at all. When the filter matched more
  than one series (several attribute sets, or several services), the query
  subtracted one series' minimum from a different series' maximum. That is
  noise, not an approximation. The chart never had this problem because it
  already grouped by series.

## Decision

**`MetricAlertConditionQueryBuilder`'s Sum branch (`BuildSumSql`) uses
ADR-0035's exact approach, collapsed to one scalar.** A `WITH ranked AS
(...)` CTE computes `row_number()` and a `lagInFrame(Value)` delta per row,
partitioned by the full `(ServiceName, toString(DataPointAttributes))`
counter identity and ordered by `Time`. The outer query applies the same
five-way `multiIf` classification (delta → `Value`; first row → `0`;
non-monotonic → raw delta; negative delta on a monotonic counter → `Value`
as reset compensation; otherwise the raw delta) and takes one `sum()` over
all rows, with no `GROUP BY`.

The result is the total increase across every matched series over the
window. `count()` (`MetricAlertAggregation.Count`) and `any(Unit)` are
unchanged, and so are the column order and types (`Float64`, `UInt64`,
`String`). `AlertQueryService.EvaluateMetricConditionAsync`'s positional
reads needed no change. Gauge and Histogram are unchanged.

## Alternatives considered

- **Share one SQL-building helper with `MetricSeriesQueryBuilder.BuildSumSql`.**
  Rejected for now. The two queries differ in their outer shape
  (bucketed/grouped/top-N-capped vs. a single scalar), and the only shared
  part is a short CTE plus a `multiIf`. Extracting it would couple the two
  builders' SQL string layouts for about ten lines of reuse. Revisit if a
  third caller appears.
- **Per-series max-over-window (for example "alert if any single series
  increased by more than N").** A different, new alert semantic, not a fix
  for the existing one. Summing across matched series is what the chart's
  ungrouped total and the old expression's *intent* both mean. Narrowing to
  one series is already possible through the condition's `MetricFilter`.

## Consequences

- Sum-condition evaluation is now a CTE with two window functions per row
  instead of a flat aggregate. The cost is bounded by the evaluation window
  (typically minutes) and the ClickHouse execution caps every query already
  sets.
- Existing Sum-type alert rules may change behavior after upgrade. Rules
  whose filters matched several series, or whose metrics use delta
  temporality, now compare against a correct (usually very different) value.
  This is a fix, but a rule tuned to the old numbers may need its threshold
  re-checked.
- Live-verified against a real ClickHouse 26.8.2.7 instance using the SQL
  generated by the builder itself, run on the real `metrics_sum` schema
  (`db/clickhouse/0008_metrics.sql`):

  | Scenario | Old `max - min` | New |
  |---|---|---|
  | Monotonic reset `100, 110, 120, 5, 15` | 115 | 35 |
  | Two series increasing by 10 and 50 | 1000 | 60 |
  | Delta temporality `5, 5, 5` | 0 | 15 |
  | UpDownCounter `10, 4, 7` | 6 | -3 |
  | Empty window | 0 (one row) | 0 (one row) |

- The gap ADR-0035 left open is closed. No wire-contract, migration, or
  dashboard change.
