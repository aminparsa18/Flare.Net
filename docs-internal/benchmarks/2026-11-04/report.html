Serialization benchmarks

JSON vs MemoryPack, Flare.Api → dashboard · run 2026-11-04 · Intel(R) Core(TM) i5-1038NG7 CPU @ 2.00GHz · commit 141af05196fc

Summary

  • .NET (Flare.Api) codec: MemoryPack encodes 2.41× – 22.7× and decodes 2.89× – 31.1× faster than System.Text.Json across the response scenarios (ratio = JSON time ÷ MemoryPack time).
  • Dashboard decode (Node 26.5.0, V8 14.6.202.34-node.24): bytes → UI types takes 1.23× – 3.31× as long with MemoryPack as with TextDecoder + JSON.parse + mapping (ratio = MemoryPack time ÷ JSON time; above 1 means JSON is faster).
  • Server memory per response (production write path, uncompressed): JSON allocates 2.5 kB – 25.2 kB and triggers 0 gen2 GCs per 1,000 responses; MemoryPack allocates 3.7 kB – 188.0 kB and triggers 0 – 181. JSON streams through pooled buffers; MemoryPack builds the whole body as one array, which lands on the Large Object Heap once it reaches 85,000 bytes.
  • Payload size, MemoryPack vs JSON (negative = MemoryPack smaller): uncompressed: -44% – -21%; gzip-6: -17% – +1%; brotli-4: -22% – +6%.
  • End to end (server encode + compression + modeled transfer + client decompress/decode/map), comparing each format at its own best codec: JSON is faster in 10 of 20 scenario × link-speed cells, MemoryPack in 10. See the matrix below.
  • Compression - scenarios where the fastest overall combination is a compressed one, per link: 1 Gbps: 4/5, 100 Mbps: 5/5, 20 Mbps: 5/5, 5 Mbps: 5/5.

Method and caveats

  • Medians throughout (BenchmarkDotNet Median, tinybench p50); means, error margins and allocations are in the table views and results.json.
  • Server stage runs the production ApiSerialization.Write → IResult.ExecuteAsync path into an in-memory response, through a GZipStream/BrotliStream the way UseResponseCompression wraps the body. Compress = that minus the uncompressed case. ClickHouse query time is excluded (the same for both formats).
  • Client stage runs in Node's V8 (the engine Chrome and Edge use), not a browser. MemoryPack: generated decoder + the production mapper exported from src/lib/*-api.ts. JSON: TextDecoder + JSON.parse + a field-by-field mapper into the same UI types; both are checked to produce identical data before timing. Decompress = that minus the uncompressed case.
  • Transfer is modeled from compressed bytes at fixed link speeds; it ignores RTT, TCP slow start and protocol overhead, and assumes the link is the bottleneck.
  • Fixtures: captured scenarios come from seeded demo data, whose attribute bags are lighter than many production workloads; the synthetic logs page models a heavier, more typical OTel attribute set. Large traces are assembled from captured spans because seeded traces are tiny.
  • Server and client stages are measured on the same machine; a real deployment has a server CPU and a (usually slower) client device.
