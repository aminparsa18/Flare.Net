# Как извлекать или скрывать поля при приёме данных

Настройте **правила конвейера** — извлечение и редактирование на основе
регулярных выражений, применяемые к логам до их записи в хранилище.
Используйте извлечение, чтобы вытащить структурированное поле (например,
идентификатор пользователя или код статуса) из сообщения лога в настоящий,
доступный для поиска атрибут. Используйте редактирование (скрытие), чтобы
маскировать конфиденциальные данные (например, номер банковской карты или
адрес электронной почты), чтобы они никогда не сохранялись в открытом виде.
Обоснование дизайна см. в
[ADR-0033](../../docs-internal/adr/0033-pipeline-rules-extraction-redaction.md)
и [ADR-0034](../../docs-internal/adr/0034-pipeline-rules-preview.md) (режим
предпросмотра).

Правила конвейера выполняются один раз, при приёме — до кластеризации
шаблонов Drain и до записи в ClickHouse. Просмотрите правило перед
сохранением (см. [Предпросмотр правила перед сохранением](#предпросмотр-правила-перед-сохранением)
ниже), чтобы убедиться, что оно ведёт себя ожидаемым образом, а не
сохранять его вслепую.

## Требования

- Работающий экземпляр Flare, доступный в браузере (любой из вариантов:
  [автономный](run-standalone.ru.md), [Aspire](run-with-aspire.ru.md) или
  через [CLI](run-with-cli.ru.md)), с уже поступающими данными.

## Создание правила редактирования (скрытия)

1. Откройте **Pipeline Rules** в верхней навигации.
2. Нажмите **New rule**. Задайте имя (например, «Скрыть номера карт»).
3. В разделе **Applies to** при желании сузьте правило до конкретных
   сервисов или уровней логов, либо оставьте без условия (см.
   [Ограничьте область действия правила](#ограничьте-область-действия-правила-не-оставляйте-его-без-условия)).
4. В разделе **Actions** выберите **Redact** и введите регулярное выражение
   для поиска (например, `\d{16}` для 16-значного номера карты). Оставьте
   поле источника пустым, чтобы скрывать `Body`, либо укажите ключ
   атрибута, чтобы вместо этого скрывать значение этого атрибута. Текст
   замены по умолчанию — `***`.
5. Нажмите **Create rule**.

С этого момента у каждого лога, соответствующего правилу, найденный текст
заменяется перед записью — включая шаблон, который вычисляет функция
кластеризации логов Drain, так что скрытое содержимое тела лога не
просочится и в шаблон кластера.

## Создание правила извлечения

1. Откройте **Pipeline Rules** → **New rule**.
2. В разделе **Actions** выберите **Extract fields** и введите регулярное
   выражение с **именованными группами захвата** — имя группы напрямую
   становится ключом нового атрибута. Например, `user_id=(?<user_id>\d+)`
   для тела вида «...for user_id=42...» добавит атрибут лога
   `user_id: "42"`.
3. Нажмите **Create rule**.

Извлечённые атрибуты отображаются как любой другой атрибут лога —
доступны для фильтрации в Logs Explorer, могут использоваться как условие
правила оповещения, точно так же, как атрибут, заданный самим исходным
приложением.

## Предпросмотр правила перед сохранением

Нажмите **Preview** в диалоге создания/редактирования в любой момент
заполнения — для этого не нужно сначала сохранять правило. Flare получает
до 20 самых свежих логов, уже соответствующих условию **Applies to**
правила, и применяет к каждому из них настроенные вами действия, в
процессе, ничего не сохраняя и не затрагивая реальный трафик приёма
данных. Вы увидите сводку («N из 20 отобранных логов изменятся») и текст
до/после для каждого отобранного лога, с пометкой изменённых.

Предпросмотр всегда выполняется по текущим, ещё не сохранённым значениям
полей диалога — даже при редактировании уже сохранённого правила, — чтобы
отражать именно тот шаблон, который вы сейчас вводите, а не последнюю
сохранённую версию. Если ни один лог сейчас не соответствует условию,
предпросмотр сообщит об этом, а не покажет пустой список; попробуйте
расширить условие или выбрать сервис, который точно активно логирует.

## Ограничьте область действия правила (не оставляйте его без условия)

Правило без фильтра по сервису, уровню или поисковому запросу применяется
**ко всем** логам — форма создания/редактирования в этом случае показывает
явное предупреждение, чтобы это было осознанным решением, а не случайностью.
Предпочтительнее ограничивать правило конкретным сервисом (сервисами), для
которого оно предназначено, особенно пока вы ещё не убедились, что новый
шаблон ведёт себя ожидаемым образом.

## Порядок выполнения при нескольких подходящих правилах

Правила выполняются в порядке их создания, каждое получает на вход
результат предыдущего. Если нужно извлечь поле из *исходного* тела до того,
как другое правило его скроет, создайте правило извлечения первым.

## Отключение правила без удаления

Переключите **Enabled** в диалоге создания/редактирования (строка правила в
таблице покажет значок **Disabled**). Отключённое правило остаётся
сохранённым, но перестаёт применяться — удобно для приостановки правила во
время расследования без потери его настроек.

## Изменения применяются не сразу

Новому, изменённому или отключённому правилу требуется до 30 секунд, чтобы
вступить в силу — `Flare.Ingest` опрашивает изменения правил с этим
интервалом, а не получает уведомление мгновенно. Этот интервал фиксирован и
пока не настраивается из панели управления.
