# 如何使用追踪漏斗找出请求流失的环节

追踪漏斗会让请求依次经过一组有序步骤，例如下单 → 支付 → 确认。对每个步骤，它会显示有多少条追踪到达该步骤、有多少在下一步之前流失、有多少在该步骤出错，以及从上一步骤过渡到该步骤耗时多久。

漏斗使用 Flare 已存储的 span。你无需修改埋点，漏斗对定义之前存储的 span 同样有效。

## 前提条件

- 一个正在运行、并接收你的应用追踪数据的 Flare 实例。
- 要追踪的步骤必须发生在**同一条追踪**中。相关服务之间需要传播追踪上下文，OpenTelemetry 的 HTTP、gRPC 和消息队列埋点默认都会这样做。

## 定义步骤

1. 在顶部导航中打开 **追踪**，然后打开 **漏斗** 标签页。
2. 为每个步骤设置以下任意条件：
   - **服务**：span 的 `service.name`，需完全一致。
   - **span 名称**：span 的名称（操作），需完全一致，例如 `POST /checkout`。
   - **属性** 过滤条件：span、资源或作用域属性，运算符与追踪浏览器相同（等于、正则、属于其中之一、存在等）。

   当 span 满足该步骤的所有条件时即与该步骤匹配。每个步骤至少需要一个条件。两个输入框都会提示所选时间窗口内出现过的值。
3. 使用 **添加步骤** 最多添加六个步骤，并用箭头调整顺序。
4. 选择时间窗口（5 分钟到 24 小时），然后点击 **运行**。

## 查看结果

| 列 | 含义 |
|---|---|
| 追踪 | 按顺序到达该步骤及之前所有步骤的追踪数，以及其占步骤 1 进入追踪数的比例 |
| 相对上一步 | 上一步骤的追踪中到达该步骤的比例 |
| 此后流失 | 到达该步骤但未到达下一步骤的追踪数 |
| 错误 | 该步骤的 span 状态为错误的追踪数 |
| p50 / p95 转化耗时 | 从上一步骤 span 开始到该步骤 span 开始的时间。将鼠标悬停可查看平均值和 p99 |

点击 **追踪**、**此后流失** 或 **错误** 下的数字，即可按从新到旧的顺序列出这些追踪（最多 100 条）。点击追踪 ID 可打开其瀑布图。

编辑步骤时漏斗不会重新运行。修改步骤后请再次点击 **运行**。更改时间窗口会重新运行漏斗。

### 步骤如何匹配

追踪以其最早匹配步骤 1 的 span 进入漏斗。之后的每个步骤使用最早一个开始时间不早于上一步骤 span 的匹配 span：

- *仅*发生在上一步骤*之前*的步骤不计入。
- 如果上一步骤之后有多个 span 匹配，则以第一个为准。如果一次支付失败而重试成功，该追踪会到达支付步骤并在该步骤计为错误，耗时计算到失败的那次尝试。
- 同一个 span 不能同时满足两个相邻的步骤。

只有在时间窗口内开始的 span 才会参与计算。在窗口结束时仍在进行中的追踪可能会显示为已流失。

## 保存和分享漏斗

使用 **视图** → **保存当前视图** 保存步骤和时间窗口。已保存的漏斗会出现在本页的视图菜单和 **视图** 页面中。从那里复制的链接会打开并运行该漏斗。本页会重新打开你上次选择的漏斗。

## 故障排查

**没有追踪到达步骤 1。** 请在追踪浏览器中对照一条追踪核对服务和 span 名称。两者都必须完全一致，包括大小写。

**所有追踪都在某一步流失，但追踪看起来是完整的。** 这两个服务可能各自开启了独立的追踪，而不是同一条。从明细列表中打开一条追踪，检查下一步骤的 span 是否在其中。

**时间窗口较长时漏斗运行很慢。** 漏斗会对窗口内匹配任一步骤的所有 span 进行分组。请为每个步骤指定服务，让 Flare 跳过其他服务的数据，或者使用更短的时间窗口。
