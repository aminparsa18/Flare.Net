# 如何分诊错误

**Errors** 页面按类型和消息对异常分组。你可以把每个分组标记为已解决或已忽略，分配给某人，并在“已修复”的错误再次出现时得到提示。

## 更改分组状态

打开行末的 **⋯** 菜单：

- **Mark resolved**：你认为已修复。Flare 会记录该分组在过去 30 天内出现过的 `service.version` 值。
- **Ignore**：隐藏该分组，并使异常计数告警规则不再统计它。可选时长：直到重新打开、24 小时、7 天，或再出现 100 次。
- **Reopen**：恢复为 Open。
- **Assign to me** / **Unassign**：记录谁在处理。

更改状态需要 Member 或 Admin 角色。Viewer 能看到状态，但看不到菜单。

## 关联工单

打开 **⋯** 菜单并选择 **关联工单…**,粘贴跟踪该分组的工单 URL(GitHub、GitLab、Jira 或任何 http(s) 地址)。状态列随后会显示类似“工单 #42”的链接;**移除工单链接**可清除。

如果该分组的服务已为[堆栈跟踪源码链接](link-exceptions-to-source-code.md)配置了 GitHub 或 GitLab 仓库,菜单中还会出现 **新建 GitHub 工单** 或 **新建 GitLab 工单**。它会打开代码托管平台的新建工单页面,并预先填好标题和简短说明(异常、服务、次数以及指回 Flare 的链接)。Flare 本身不会调用该平台,因此由您以自己的身份创建工单,再把它的 URL 粘贴到 **关联工单…** 中。

对于 Jira,管理员需要为服务配置一次:打开该服务某个错误的出现记录,使用源码链接图标旁的工单图标,填写 Jira 站点 URL(例如 `https://acme.atlassian.net`)、数字 **项目 ID**,以及可选的数字 **工单类型 ID**。项目 ID 是项目设置 URL 中的数字,或您的站点上 `/rest/api/2/project/<KEY>` 返回的 `id`。之后菜单会出现 **新建 Jira 工单**,它会打开 Jira 的创建页面并预先填好摘要和说明。与 GitHub、GitLab 一样,Flare 不会调用 Jira,因此由您以自己的身份创建工单,再把它的 URL 粘贴到 **关联工单…** 中。

## 自动分配负责人

点击工具栏中的 **归属规则**,把错误映射到人。每条规则用不区分大小写的模式匹配 **服务** 名称或 **异常类型**,其中 `*` 代表任意文本,例如 `payments-*` 或 `*Timeout*`,并填写负责人的用户名。规则从上到下依次检查,第一条匹配的规则拥有该分组,显示为“负责人 alice(规则)”。可用箭头调整顺序。

第三种类型 **文件路径** 使用 [CODEOWNERS](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners) 路径语法匹配分组堆栈跟踪中的源文件:`/src/payments/`(仓库根目录下的目录)、`*.sql`(任意深度)、`docs/*.md`、`src/**/Charge.cs`。Flare 从每个分组的一条示例堆栈跟踪中读取文件路径,因此只有带文件信息的栈帧才有效(.NET 需要符号,或带源码路径的确定性构建)。构建机上的检出位置无关紧要,因为模式会与每个路径的所有尾部片段比对。

**导入 CODEOWNERS** 会把粘贴的 CODEOWNERS 文件转换为文件路径规则。每行取第一个负责人并去掉开头的 `@`,顺序会被反转,因为 CODEOWNERS 以靠后的行为准,而 Flare 取第一条匹配。负责人只有与 Flare 用户名一致才有用,保存前请检查列表。

通过 **分配给我** 指定的人始终优先于规则。规则不会作为已保存的分配记录:修改规则后,显示的负责人也随之改变。

## 回归

已解决的分组如果在它此前未出现过的 `service.version` 中再次出现，会显示为 **Regressed** 并标明版本。在已知版本中再次出现不算：修复很可能还没部署到该实例。如果你的服务不上报 `service.version`，已解决分组的任何新出现都算作回归。

## 按状态筛选

服务筛选旁边的状态筛选默认为 **Active**，会隐藏已忽略的分组。选择 **All statuses** 或某个单一状态可查看其余分组。

旁边的 **我的错误** 只显示由您负责的分组：分配给您的，或在没有指派人时由归属规则判给您的。关闭登录时该按钮会隐藏，因为没有当前用户。该选择会记在当前浏览器中，打开 `/errors?mine=1` 即可直接启用此筛选。

## 告警

异常计数告警规则不统计已忽略的分组，事件摘要也会略去它们。更改自规则的下一次评估起生效。忽略到期后，该分组会重新被统计。

异常计数告警通知还会说明错误的负责人。它查看窗口内最频繁的三个分组，并添加一行 `Owner:`，内容为每个分组的指派人，没有时则为第一条匹配的归属规则（服务、异常类型或堆栈跟踪路径）所指定的人，同名不重复。相同的值可在[通知模板](../alerting/share-alert-notification-templates.zh-CN.md)中用 `{{owner}}` 引用，无人负责时为空，AI 事件摘要也会获得它。

## 调整错误的分组方式

在 Errors 页面点击**分组规则**（需要 Member 或 Admin）。有三项设置，按以下顺序生效：

1. **折叠 ID、数字和引号内的值**即上文的自动规范化。如果它把你想区分的错误合并了（例如 `HTTP 404` 和 `HTTP 500`），可以关闭。
2. **替换**规则用正则表达式（[RE2 语法](https://github.com/google/re2/wiki/Syntax)）和替换文本改写每条消息的一部分，其中 `\1` 表示第一个捕获组。把 `user [a-z]+` 替换为 `user <name>`，`user alice denied` 和 `user bob denied` 就成为同一个分组。规则按列表顺序在自动规范化之后运行，对所有消息生效，与异常类型无关。
3. **合并**把一个分组并入另一个异常类型相同的分组。打开某一行的菜单，选择**合并到另一个分组…**，再选目标分组。合并以规则形式保存，因此也适用于之后出现的异常，并显示在同一个对话框中。

保存时会检查每个表达式。无法编译、能匹配空字符串，或替换文本又能匹配该模式的规则会被拒绝，并给出原因。

分诊状态跟随分组。规则变化后，已解决、已忽略和已指派的状态会迁移到消息现在所属的分组；多个分组合并为一个时，以最近一次变更的为准。删除规则或关闭规范化会再次拆开分组，但不会恢复被合并分组原有的状态：这些分组从 Open 开始。

## 限制

分组由类型加规范化后的消息构成。分组之前，Flare 会把消息中会变化的部分替换成占位符：GUID（`<guid>`）、`0x` 十六进制值（`<hex>`）、ISO-8601 时间戳（`<ts>`）、引号内的值（`'<s>'`）以及独立的数字（`<n>`）。`Order 4812 not found` 和 `Order 77 not found` 属于同一个分组，显示为 `Order <n> not found`；打开分组即可看到每次出现各自的消息。只是包含数字的标识符，例如 `HTTP2` 或 `sha256`，不会被改动。

如果消息中变化的部分是单词，而不是数字、ID 或引号内的值（例如用户名、主机名），不会被自动折叠；参见[调整错误的分组方式](#调整错误的分组方式)。

分诊状态跟随规范化后的分组。升级时，以旧的完整消息保存的状态会迁移到新分组（迁移 `0087`）：多个旧分组合并为一个时，以最近一次变更的为准。异常数量告警规则按同样方式比较消息，因此消息为 `Order 4812 not found` 的规则现在也会覆盖其他订单 ID。
