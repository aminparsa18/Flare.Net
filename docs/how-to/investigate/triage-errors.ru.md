# Как разбирать ошибки

Страница **Errors** группирует исключения по типу и сообщению. Каждую группу можно пометить решённой или игнорируемой, назначить на человека и узнать, когда «исправленная» ошибка вернулась.

## Изменить статус группы

Откройте меню **⋯** в конце строки:

- **Mark resolved**: вы считаете, что ошибка исправлена. Flare запоминает значения `service.version`, в которых группа встречалась за последние 30 дней.
- **Ignore**: скрывает группу и исключает её из подсчёта в правилах оповещений по числу исключений. Выберите срок: пока не откроете снова, 24 часа, 7 дней или ещё 100 повторений.
- **Reopen**: возврат в Open.
- **Assign to me** / **Unassign**: отметить, кто этим занимается.

Менять статус могут роли Member и Admin. Viewer видит статус, но не меню.

## Привязать задачу

Откройте меню **⋯** и выберите **Привязать задачу…**, чтобы вставить URL задачи, которая отслеживает группу (GitHub, GitLab, Jira или любой адрес http(s)). В ячейке статуса появится ссылка вида «Задача #42»; **Убрать ссылку на задачу** удаляет её.

Если для сервиса группы настроен репозиторий GitHub или GitLab для [ссылок на исходный код в стек-трейсах](link-exceptions-to-source-code.md), в меню также есть **Новая задача в GitHub** или **Новая задача в GitLab**. Она открывает страницу создания задачи на этом хостинге с уже заполненными заголовком и кратким описанием (исключение, сервисы, счётчики и ссылка на Flare). Эта ссылка не обращается к хостингу: вы создаёте задачу от своего имени и затем вставляете её URL в **Привязать задачу…** (или [создаёте её из Flare](#создание-задачи-из-flare)).

Для Jira администратор настраивает сервис один раз: откройте любое вхождение его ошибки и значком билета рядом со значком ссылки на исходный код введите URL сайта Jira (например, `https://acme.atlassian.net`), числовой **ID проекта** и, при желании, числовой **ID типа задачи**. ID проекта - это число в URL настроек проекта или поле `id` ответа `/rest/api/2/project/<KEY>` на вашем сайте. После этого в меню появится **Новая задача в Jira**: она открывает страницу создания в Jira с заполненными заголовком и описанием. Как и для GitHub и GitLab, эта ссылка не обращается к Jira: вы создаёте задачу от своего имени и вставляете её URL в **Привязать задачу…**.

### Создание задачи из Flare

Ссылки выше создают задачу от вашего имени. Чтобы Flare сам создавал задачу и сразу привязывал её, администратор добавляет **отдельный** токен с правом записи, а не токен только для чтения из ссылок на исходный код:

- **GitHub / GitLab:** в форме со значком ссылки у вхождения заполните **Токен с правом создавать задачи**. Для GitHub нужен fine-grained токен с правом *Issues: read and write* на репозиторий; в GitLab нет области уже, чем `api`, поэтому используйте токен доступа проекта. В репозиториях Azure DevOps задачи создать нельзя.
- **Jira:** в форме со значком билета введите **API-токен** и числовой **ID типа задачи** (для создания он обязателен; для заранее заполненной ссылки его можно оставить пустым). Для Jira Cloud укажите ещё **email** аккаунта, которому принадлежит токен; если email пуст, токен отправляется как персональный токен доступа Server/Data Center.

Токены хранятся в зашифрованном виде и больше не показываются; оставьте поле пустым, чтобы сохранить токен, а очистить его можно, сохранив пустое значение через API. Когда токен задан, в меню для группы без привязанной задачи появляется **Создать задачу в GitHub**, **Создать задачу в GitLab** или **Создать задачу в Jira** (рядом со ссылками «Новая задача…»). API Flare создаёт задачу с тем же заголовком и описанием, что и в заранее заполненной ссылке, сохраняет её URL как ссылку группы и показывает как «Задача #42». Автором задачи будет аккаунт токена, а не вы; в журнале аудита записано, кто нажал.

Flare обращается только к репозиторию или сайту Jira, которые настроил администратор, не следует перенаправлениям и сдаётся через 10 секунд без повторных попыток. Если у группы уже есть ссылка или её задача ещё создаётся, запрос отклоняется, чтобы двойной щелчок не создал две задачи. Если адрес хоста частный (self-hosted GitLab или Jira в вашей сети), разрешите его на Flare.Api через `Outbound__Allow__0=git.corp.local` (см. [руководство по пересылке](../data/forward-telemetry-to-another-otlp-endpoint.md)).

## Автоматически назначать владельцев

Нажмите **Правила владения** на панели, чтобы сопоставить ошибки с людьми. Каждое правило сопоставляет имя **сервиса** или **тип исключения** по шаблону без учёта регистра, где `*` заменяет любой текст, например `payments-*` или `*Timeout*`, и указывает имя пользователя владельца. Правила проверяются сверху вниз, группой владеет первое подошедшее; в таблице это «Владелец alice (правило)». Порядок меняется стрелками.

Третий тип, **Путь к файлу**, сопоставляет исходные файлы из стек-трейса группы по синтаксису путей [CODEOWNERS](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners): `/src/payments/` (каталог в корне репозитория), `*.sql` (на любой глубине), `docs/*.md`, `src/**/Charge.cs`. Flare берёт пути из одного образца стек-трейса на группу, поэтому учитываются только кадры с информацией о файле (для .NET нужны символы или детерминированная сборка с путями к исходникам). Расположение репозитория на сборочной машине не важно: шаблон проверяется на каждом хвосте пути.

**Импорт CODEOWNERS** превращает вставленный файл CODEOWNERS в правила «Путь к файлу». Из каждой строки берётся первый владелец без ведущего `@`, а порядок меняется на обратный: в CODEOWNERS побеждает последняя строка, а во Flare первое совпадение. Владельцы полезны, только если совпадают с именами пользователей Flare, поэтому проверьте список перед сохранением.

Исполнитель, назначенный через **Назначить мне**, всегда важнее правила. Правила не сохраняются как назначения: измените правило, и показанный владелец изменится вместе с ним.

## Регрессии

Решённая группа, которая повторилась в `service.version`, где раньше не встречалась, отображается как **Regressed** с указанием версии. Повторение в уже известной версии не считается: исправление, скорее всего, ещё не дошло до этого экземпляра. Если сервисы не передают `service.version`, любое новое появление решённой группы считается регрессией.

## Фильтр по статусу

Фильтр статуса рядом с фильтром сервисов по умолчанию равен **Active** и скрывает игнорируемые группы. Выберите **All statuses** или один статус, чтобы увидеть остальные.

**Мои ошибки** рядом показывает только группы, которыми владеете вы: назначенные вам или, если исполнителя нет, закреплённые за вами правилом владения. Кнопка скрыта, когда вход отключён, потому что текущего пользователя нет. Выбор запоминается в этом браузере, а `/errors?mine=1` открывает страницу с включённым фильтром.

## Оповещения

Правила оповещений по числу исключений не считают игнорируемые группы, и сводка инцидента их не включает. Изменение действует со следующей проверки правила. Когда срок игнорирования истекает, группа снова учитывается.

Оповещение по числу исключений также называет владельца ошибки. Оно смотрит на три самые частые группы окна и добавляет строку `Owner:` с исполнителем каждой группы или, если его нет, с владельцем из первого подходящего правила владения (сервис, тип исключения или путь из стек-трейса), не повторяя имён. То же значение доступно как `{{owner}}` в [шаблонах уведомлений](../alerting/share-alert-notification-templates.ru.md), оно пусто, если группами никто не владеет, и ИИ-сводка инцидента получает его тоже.

## Как изменить группировку ошибок

Нажмите **Правила группировки** на странице Errors (роль Member или Admin). Три настройки применяются в таком порядке:

1. **Сворачивать идентификаторы, числа и значения в кавычках** — это описанная выше автоматическая нормализация. Выключите её, если она объединяет ошибки, которые вы хотите различать, например `HTTP 404` и `HTTP 500`.
2. Правила **Замена** переписывают часть каждого сообщения регулярным выражением ([синтаксис RE2](https://github.com/google/re2/wiki/Syntax)) и заменой, где `\1` — первая группа захвата. Замена `user [a-z]+` на `user <name>` делает `user alice denied` и `user bob denied` одной группой. Правила выполняются по порядку списка, после автоматической нормализации, для всех сообщений независимо от типа исключения.
3. **Объединение** вливает одну группу в другую с тем же типом исключения. Откройте меню строки, выберите **Объединить с другой группой…** и укажите целевую. Объединение сохраняется как правило, поэтому действует и на будущие случаи и видно в том же окне.

При сохранении проверяется каждое выражение. Шаблон, который не компилируется, совпадает с пустой строкой или чья замена снова совпадает с шаблоном, отклоняется с указанием причины.

Состояние триажа следует за группами. При изменении правил состояние «решено», «игнорируется» и назначение переходит в группу, к которой теперь относится сообщение; если несколько групп сливаются в одну, побеждает изменявшаяся последней. Удаление правила или отключение нормализации снова разделяет группы, но не возвращает состояние, которое было у объединённой группы: такие группы начинаются со статуса Open.

## Ограничения

Группа — это тип плюс нормализованное сообщение. Перед группировкой Flare заменяет изменяющиеся части сообщения заполнителями: GUID (`<guid>`), шестнадцатеричные значения `0x` (`<hex>`), метки времени ISO-8601 (`<ts>`), значения в кавычках (`'<s>'`) и отдельно стоящие числа (`<n>`). `Order 4812 not found` и `Order 77 not found` попадают в одну группу, которая отображается как `Order <n> not found`; откройте группу, чтобы увидеть собственное сообщение каждого случая. Идентификаторы, в которых просто есть цифры, например `HTTP2` или `sha256`, не меняются.

Если изменяющаяся часть сообщения — слово, а не число, идентификатор или значение в кавычках (имя пользователя, имя хоста), автоматически она не сворачивается; см. [Как изменить группировку ошибок](#как-изменить-группировку-ошибок).

Состояние триажа привязано к нормализованной группе. При обновлении состояние, сохранённое под прежними точными сообщениями, переносится на новые группы (миграция `0087`): если несколько прежних групп сливаются в одну, побеждает та, что менялась последней. Правила оповещений по числу исключений сравнивают сообщение так же, поэтому правило с сообщением `Order 4812 not found` теперь охватывает и другие идентификаторы заказов.
