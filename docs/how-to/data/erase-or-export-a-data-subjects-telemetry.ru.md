# Как удалить или экспортировать телеметрию одного человека

Retention удаляет телеметрию по возрасту. Когда человек просит удалить свои данные (GDPR, ст. 17) или передать их ему (ст. 15), их нужно удалить или экспортировать по принадлежности. Flare сопоставляет строки по атрибутам, таким как `user.id`, `user.email` или `client.address`, в логах, спанах (включая события исключений), метриках, профилях и в остальных данных сессий пользователя, включая скриншоты и отзывы. Сделать это может только Admin.

Это можно сделать в дашборде в **Settings > Data erasure**, а также через CLI `flare erasure` и API `/api/erasure`.

Flare находит только те данные, в которых идентификатор записан как атрибут. Если ваше приложение никогда не записывает `user.email`, поиск по адресу электронной почты ничего не найдёт.

## В дашборде

1. Откройте **Settings**, затем **Data erasure** в разделе Workspace.
2. Введите один или несколько идентификаторов (ключ и значение атрибута), например `user.id` = `42`. Чтобы добавить ещё, выберите **Add identifier**.
3. Выберите **Preview**, чтобы увидеть подходящие строки по таблицам, или **Export**, чтобы скачать их в формате NDJSON.
4. Чтобы удалить, введите значение первого идентификатора в поле подтверждения и выберите **Erase**. Пока предпросмотр не соответствует текущим идентификаторам, кнопка остаётся неактивной.

Список **Erasure requests** ниже показывает каждый запрос с прогрессом по таблицам и обновляется, пока идёт удаление.

В следующих разделах те же шаги показаны через CLI.

## Предпросмотр того, что будет удалено

```bash
flare erasure preview --id user.id=42 --id user.email=jane@example.com
```

Каждый `--id КЛЮЧ=ЗНАЧЕНИЕ` — один идентификатор одного и того же человека. Строка принадлежит ему, если совпал любой из идентификаторов. Сопоставление — точное равенство по атрибуту ресурса, области (scope), лога, спана, точки данных или события спана. Команда выводит количество подходящих строк по таблицам.

Сессии отслеживаются тоже: Flare находит `session.id` каждого подходящего лога и спана, а затем сопоставляет и строки с одним из этих идентификаторов сессий. Поэтому строки логов, спаны и точки метрик той же сессии включаются, даже если в них не повторяется идентификатор пользователя. Скриншоты и отзывы находятся только так, а также по собственным полям отзыва с идентификатором пользователя и адресом электронной почты. Если подходит более 10 000 сессий, предпросмотр предупреждает, что остальные не охвачены.

Тот же вызов — `POST /api/erasure/preview` с телом `{"identifiers": [{"key": "user.id", "value": "42"}]}`.

## Экспорт данных

```bash
flare erasure export --id user.id=42 --output subject-42.ndjson
```

Экспорт — JSON с разделением строк переводом строки: одна строка `{"table": "logs", "row": {...}}` на каждую строку данных. Для таблицы действует лимит 100 000 строк; урезанная таблица заканчивается строкой `{"table": "logs", "truncated": true}`, после чего можно сузить запрос или экспортировать снова. В API это `POST /api/erasure/export`.

Если человек просил и то и другое, сначала экспортируйте, затем удаляйте.

## Удаление данных

```bash
flare erasure run --id user.id=42 --id user.email=jane@example.com --confirm 42
```

`--confirm` должно совпадать со значением первого `--id`, чтобы случайная команда ничего не удалила. Удаление необратимо.

API принимает запрос с ответом `202` и идентификатором транзакции, затем ставит в очередь по одному `ALTER TABLE ... DELETE` ClickHouse на каждую таблицу с подходящими строками. ClickHouse перезаписывает затронутые части данных в фоне, поэтому на большой таблице это может занять много времени. CLI по умолчанию ждёт и выводит прогресс; передайте `--no-wait`, чтобы вернуться сразу и проверить позже:

```bash
flare erasure status            # последние запросы
flare erasure status <id>       # один запрос, по таблицам
```

Для каждой таблицы показывается `pending`, `running`, `success` или `failed` и сколько частей данных удалению ещё предстоит перезаписать. Запрос получает `success`, когда завершено удаление во всех таблицах. Одновременно можно отправить только один запрос; второй получит `409`, пока первый не поставит свои удаления в очередь.

## Что остаётся

- **Агрегаты.** Карты сервисов, SLO, дашборды и другие предварительно агрегированные таблицы содержат счётчики и квантили без идентификаторов, поэтому не меняются.
- **Резервные копии и архивы.** Данные, уже переданные на другую точку OTLP или заархивированные в S3, находятся вне Flare. Удаляйте их там.
- **Строки без атрибута.** Строка лога, где человек упоминается только в тексте сообщения, не находится. Найдите её в Logs.
- **Строки, принятые после запроса.** Удаление затрагивает то, что существует на момент выполнения. Не позволяйте источнику отправлять идентификатор или добавьте [правило конвейера](manage-pipeline-rules.ru.md), которое его скроет.

## Журнал аудита

Каждое удаление и каждый экспорт записываются в журнал аудита (Settings > Audit log): кто выполнил, когда, какие ключи атрибутов использовались и короткий хеш значений. Сами значения не сохраняются, потому что это и есть персональные данные. Запросы хранятся в истории удалений три года как подтверждение того, что они были обработаны.

Описание дизайна см. в [ADR-0198](../../../docs-internal/adr/0198-data-subject-erasure-export.md).
