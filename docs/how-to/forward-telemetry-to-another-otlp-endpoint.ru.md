# Как пересылать телеметрию на другой OTLP-эндпоинт

Flare может отправлять копию всего принятого на один или несколько других OTLP/HTTP-эндпоинтов, например чтобы запустить Flare рядом с другим бэкендом на время миграции или чтобы кормить второго потребителя.

## Добавьте цель в дашборде

Откройте **Настройки > Рабочее пространство > Экспорт телеметрии** (только для администраторов) и нажмите **Новая цель**. Задайте название и базовый URL эндпоинта, при необходимости добавьте заголовки (по одному `Имя: значение` в строке), выберите сигналы, сервисы и ключи приёма для пересылки и сохраните. Flare.Ingest перечитывает сохранённые цели каждые 30 секунд, поэтому новая, изменённая, отключённая или удалённая цель начинает действовать без перезапуска.

Значения заголовков после сохранения скрыты. При редактировании цели оставьте скрытое значение без изменений, чтобы сохранить его, или введите новое, чтобы заменить.

В таблице видно состояние каждой цели, оно обновляется каждые несколько секунд: сколько запросов **в очереди**, счётчики **отправлено** и **ошибок**, последняя ошибка. Цели, заданные в конфигурации, показаны под сохранёнными с пометкой *Из конфигурации*; здесь они доступны только для чтения.

## Или настройте цель в файлах

Цели можно также задать конфигурацией **Flare.Ingest** (appsettings или переменные окружения), что удобно для инфраструктуры как кода. Сохранённые цели работают вместе с ними. Через переменные окружения, которые соответствуют `Forwarding:Targets:<индекс>:<параметр>`:

```yaml
services:
  ingest:
    environment:
      Forwarding__Targets__0__Name: second-backend
      Forwarding__Targets__0__Endpoint: https://collector.example.com:4318
      Forwarding__Targets__0__Headers__Authorization: Bearer <token>
      Forwarding__Targets__0__Signals__0: Logs
      Forwarding__Targets__0__Services__0: checkout
```

Flare добавляет `/v1/logs`, `/v1/traces` или `/v1/metrics` к `Endpoint` и отправляет protobuf, сжатый gzip.

| Параметр | По умолчанию | Значение |
|---|---|---|
| `Name` | обязателен | Уникальная метка для сообщений в логе. |
| `Endpoint` | обязателен | Базовый URL принимающего OTLP/HTTP-эндпоинта (`http` или `https`). |
| `Headers` | нет | Дополнительные заголовки запроса, например `Authorization`. |
| `Signals` | все | Любые из `Logs`, `Traces`, `Metrics`. |
| `Services` | все | Пересылать только эти значения `service.name`; данные других сервисов удаляются из копии. |
| `IngestKeyIds` | любые | Пересылать только запросы, аутентифицированные этими ключами приёма (идентификаторы ключей). |
| `Gzip` | `true` | Сжимать тела запросов. |
| `Timeout` | `00:00:10` | Тайм-аут одного запроса. |
| `QueueCapacity` | `10000` | Запросов, которые хранит очередь цели в Redis; сверх этого самые старые отбрасываются. |
| `MaxAttempts` | `3` | Немедленных попыток доставки при сетевых ошибках, 429 и 5xx, после чего запрос ждёт повтора. |

Три параметра действуют на все цели и находятся прямо под `Forwarding`:

| Параметр | По умолчанию | Значение |
|---|---|---|
| `Forwarding__MaxAge` | `06:00:00` | Запрос в очереди старше этого срока отбрасывается, а не доставляется. |
| `Forwarding__ReclaimIdle` | `00:00:30` | Сколько недоставленный запрос ждёт перед повтором. |
| `Forwarding__RefreshInterval` | `00:00:30` | Как часто перечитываются сохранённые цели. |

Некорректная цель в конфигурации (неверный URL, повторяющееся имя) останавливает Flare.Ingest при запуске.

## Чего ожидать

- Пересылаются только запросы, которые Flare принял. Отклонённые (превышен лимит ключа приёма, сервис не разрешён, неверный формат) не пересылаются.
- У каждой цели своя очередь в Redis. Запрос удаляется из неё, когда получатель его принял (или ответил неповторяемой ошибкой 4xx, например 401: она засчитывается как ошибка, а запрос отбрасывается). Сетевая ошибка, 429 или 5xx оставляют запрос в очереди; он повторяется через `ReclaimIdle`, пока не станет старше `MaxAge`. Очередь переживает перезапуск Flare.Ingest, а несколько реплик Flare.Ingest делят работу между собой.
- Доставка «минимум один раз»: если запрос завершился тайм-аутом, хотя получатель его уже сохранил, повтор создаст дубликат. Если получатель недоступен дольше `MaxAge` или очередь превысила `QueueCapacity`, самые старые запросы отбрасываются. Собственная копия Flare не страдает, а медленный получатель не замедляет приём.
- Удаление или отключение цели стирает её очередь и счётчики.
- Профили не пересылаются.
- Цель с ключами приёма ничего не получает от запросов без ключа приёма.

Устройство описано в [ADR-0155](../../docs-internal/adr/0155-otlp-forwarding.md) и [ADR-0157](../../docs-internal/adr/0157-managed-telemetry-export.md).
