# Как строить в Grafana графики сессий, ошибок и состояния релизов Flare

API [Prometheus](query-with-prometheus-api.ru.md), [Loki](query-with-loki-api.ru.md) и [Tempo](query-with-tempo-api.ru.md) позволяют штатным источникам данных Grafana читать метрики, логи и трейсы Flare. Часть того, что знает Flare, не выражается в этих языках запросов: **сессии** клиентского приложения, стоящие за сбоем, **группы ошибок** и их состояние разбора, **состояние релизов** (release health) по версиям и **релизы**, которые вы отметили. Плагин источника данных Flare читает всё это, так что данные можно разместить рядом с другими панелями.

Его бэкенд работает внутри **сервера Grafana** и обращается к Flare.Api с вашим токеном, поэтому до Flare должен дотягиваться сервер Grafana, токен никогда не попадает в браузер, а запросы работают и в правилах алертов, публичных дашбордах и отчётах.

## Установка плагина

Плагина пока нет в каталоге Grafana. Нужна Grafana 13.2 или новее. У плагина есть бэкенд-компонент, поэтому установка должна содержать бинарник для вашей платформы (Linux, macOS или Windows; x64 или arm64).

**Из релиза.** В каждом [релизе GitHub](https://github.com/aminparsa18/Flare.Net/releases) `grafana-plugin-v*` есть `apardev-flare-datasource-<версия>.zip` с фронтендом и бэкендом для всех платформ. Распакуйте его в каталог плагинов Grafana, разрешите загрузку без подписи и перезапустите Grafana:

```bash
unzip apardev-flare-datasource-<версия>.zip -d /var/lib/grafana/plugins
export GF_PLUGINS_ALLOW_LOADING_UNSIGNED_PLUGINS=apardev-flare-datasource
```

**Из репозитория.** Нужны Node 22 и Go. Сначала соберите фронтенд (он очищает `dist/`), затем бэкенд (`build:linux`, `build:darwin`, `build:windows` или без цели для всех):

```bash
cd src/grafana-datasource
npm ci && npm run build
go run github.com/magefile/mage -v build:linux
```

Скопируйте `dist/` в каталог плагинов Grafana под именем `apardev-flare-datasource` и задайте ту же переменную окружения. В Docker смонтируйте `dist/` (или распакованный релиз) в `/var/lib/grafana/plugins/apardev-flare-datasource`.

## Подключение Grafana

1. Создайте [персональный токен доступа](../admin/configure-authentication.ru.md#персональные-токены-доступа).
2. В Grafana добавьте источник данных **Flare**.
3. В поле **Flare API URL** укажите базовый адрес API Flare так, как его видит сервер Grafana (`http://flare-api:8080` в сети compose Flare).
4. Вставьте токен. Оставьте поле пустым только если в Flare отключена аутентификация.
5. По желанию задайте **Flare dashboard URL**, чтобы идентификатор сессии вёл на её страницу во Flare.
6. Нажмите **Save & test**.

## Запросы

| Запрос | Результат | Параметры |
|---|---|---|
| **Sessions** | По строке на сессию клиентского приложения за выбранный период: начало, последняя активность, идентификатор, сервис, версия, ОС, устройство, спаны, трейсы, ошибки и экраны | Сервис, версия, только с ошибками |
| **Session timeline** | Спаны одной сессии в порядке начала: имя, длительность, экран, ошибка, исключение, breadcrumb и ссылка на трейс | ID сессии |
| **Errors** | Группы исключений, ранжированные по числу случаев, с первым и последним появлением, затронутыми сервисами и владельцем | Сервис, top N |
| **Error issues** | Состояние разбора групп ошибок: статус (открыта, решена, игнорируется, регрессия), исполнитель, версия регрессии и ссылка на задачу | Нет |
| **Release health** | По строке на версию приложения: сессии, сессии со сбоем и с ошибкой, пользователи, доля сессий и пользователей без сбоев | Сервис |
| **Release health trend** | По одному ряду на версию во времени | Сервис, ряд (% сессий без сбоев, сессии или сессии со сбоем), ширина интервала |
| **Releases** | Отмеченные вами деплои с коммитом, URL, заметками и числом новых ошибок и регрессий | Сервис |
| **App starts** | Длительность холодных и тёплых запусков (спаны `app.start`): число, p50 и p95 по версиям | Сервис, версия |
| **Screen performance** | По экранам: загрузки, p50 и p95 загрузки (спаны `screen.load`) и доля медленных и зависших кадров (спаны `screen.frames`) | Сервис, версия |

В поле **Service** можно указать одно имя или несколько через запятую; переменная с несколькими значениями тоже работает. Пустое поле означает все сервисы. Запросы версий и состояния релизов с несколькими сервисами выполняются по разу на сервис и добавляют столбец или лейбл Service.

## Переменные шаблона

Создайте переменную типа **Query**, выберите источник данных Flare и укажите, что она перечисляет: сервисы с сессиями, версии приложения с сессиями (при желании для одного сервиса), сервисы с ошибками или версии релизов. Используйте переменную в поле Service панели, например `$service`.

## Деплои на панели

Добавьте запрос аннотаций к источнику данных Flare с запросом **Releases**. Настройки аннотаций Grafana сопоставляют поля `time`, `title` и `text`, которые запрос отдаёт, и каждый деплой отмечается пунктирной линией. Для отметок релизов на панелях Prometheus используйте метрики `flare_release_*` и метрики аннотаций, описанные в [руководстве по API Prometheus](query-with-prometheus-api.ru.md#annotations).

## Импорт дашборда

В плагин встроен дашборд **Flare app health**: доля сессий без сбоев и число сессий по версиям во времени, здоровье релизов, запуск приложения и производительность экранов, основные ошибки, сессии с ошибками и разбор ошибок, а отмеченные вами релизы показаны аннотациями. Откройте вкладку **Dashboards** источника данных, нажмите **Import** и выберите сервисы в переменной **Service** вверху. Панели — обычные панели Grafana на описанных выше запросах, их можно свободно менять и копировать.

## Алерт по доле сессий без сбоев

**Release health trend** возвращает числовой временной ряд на каждую версию приложения (и на каждый сервис, если указано несколько), поэтому его можно использовать в правиле алертов Grafana. Создайте правило с такими запросами:

1. **A**: источник данных Flare, запрос **Release health trend**, ваш сервис, ряд **Crash-free sessions %**.
2. **B**: выражение **Reduce** над A, функция **Last**, режим **Drop non-numeric**.
3. **C**: выражение **Threshold** над B, **Is below** `99`.

Grafana вычисляет по одному экземпляру алерта на версию с метками `version` (и `service`), так что плохой релиз срабатывает отдельно. Табличные запросы (сессии, ошибки, здоровье релизов, производительность приложения) в алертах использовать нельзя: выражениям Grafana нужны временные ряды; для них есть [правила алертов](../../tutorials/first-alert.ru.md) самого Flare.

## Ограничения

- **Правилу алертов нужен временной ряд.** Его возвращает только запрос **Release health trend**; табличные запросы работают в дашбордах, публичных дашбордах и отчётах, но не в условиях алертов.
- **Не более 7 дней на запрос.** Более широкий период обрезается до последних 7 дней, и панель сообщает об этом.
- **Не более 500 сессий на запрос**, самых свежих. Сузьте сервис, версию или период, когда панель предупреждает, что список обрезан.
- **Для таймлайна сессии сессия должна попадать во временной диапазон.** Запрос ищет спаны этой сессии в диапазоне дашборда, поэтому сдвиньте диапазон на время, когда шла сессия (запрос Sessions её перечисляет).
- **Состояние релизов следует определению сессии во Flare**: сессия считается упавшей, если в ней есть вышедший за пределы `app.unhandled_exception`, а пользователи это различные значения `user.id`, как в представлении Releases во Flare.
