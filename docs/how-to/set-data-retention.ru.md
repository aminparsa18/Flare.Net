# Как задать срок хранения данных и перенести старые данные в холодное хранилище

По умолчанию Flare хранит все логи, спаны, метрики и профили вечно. Срок хранения ограничивает объём диска: у каждого сигнала есть свой срок жизни, ClickHouse удаляет строки старше него, а при желании сначала переносит устаревшие данные в более дешёвое объектное хранилище. Менять срок может только администратор; читать - любой вошедший пользователь.

## Задать срок в дашборде

1. Откройте **Settings**, затем **Retention** в разделе Workspace.
2. У каждого сигнала (logs, traces, metrics, profiles) своя карточка. В поле **Хранить (дней)** введите число дней. `0` - хранить сигнал вечно.
3. Нажмите **Применить**.

Карточка показывает **Сейчас в ClickHouse** - значение, прочитанное из базы напрямую, - и помечает **Отличается от последнего запроса**, если оно больше не совпадает с тем, что Flare применил в последний раз, например после ручной правки TTL. TTL, заданный не Flare, отображается как **Пользовательский TTL**.

Применение асинхронное. Карточка показывает **Применяется…**, пока ClickHouse не установит новый TTL, и одновременно может выполняться только одно изменение. Затем ClickHouse удаляет устаревшие данные при фоновых слияниях, поэтому место освобождается за часы, а не в момент успеха. Сокращение срока хранения нельзя отменить.

Агрегаты, на которых построены карта сервисов, SLO и дашборды (`service_metrics` и подобные), не имеют TTL, поэтому живут дольше исходных данных.

## Хранить одни ресурсы дольше, другие короче

В разделе **Правила по ресурсам** нажмите **Добавить правило** и укажите атрибут ресурса, значение и число дней, например `deployment.environment` = `dev` на `7` дней. Строки, у которых атрибут ресурса равен значению, живут столько дней. Срабатывает первое подходящее правило, а **По умолчанию (дней)** покрывает всё остальное.

- Сравнение - точное равенство по атрибуту ресурса, не префикс и не шаблон, и не по атрибутам логов или спанов.
- У сигнала не больше 20 правил.
- Правила действуют на строки в момент записи. Данные, уже слитые по старому набору правил, сохраняют выданный им срок.

## Переносить старые данные в холодное хранилище

По умолчанию холодное хранилище выключено. Чтобы включить его, запустите Flare с оверлеем cold-storage:

```bash
docker compose -f docker-compose.yml -f docker-compose.cold-storage.yml up -d
```

(`docker-compose.cold-storage.cluster.yml` - кластерный вариант; в Aspire вызовите `AddFlare().WithColdStorage()`.) Это добавляет контейнер RustFS как S3-совместимое хранилище и политику хранения ClickHouse, которая его использует. Карточка **Холодное хранилище** на странице Retention покажет диски со свободным местом, а у каждого сигнала появится поле **Переносить в холодное через (дней)**.

Задайте значение меньше срока хранения сигнала или меньше самого короткого из его правил, иначе данные удалятся до переноса. `0` - без переноса. Если срок хранения `0`, а перенос задан, данные переносятся в холодное хранилище и никогда не удаляются.

Холодные данные остаются в той же таблице, поэтому поиск, оповещения и дашборды продолжают работать; чтение из холодного хранилища медленнее. Перенос идёт в фоне, минуты или часы. Если позже выключить перенос, правило переноса удаляется, а части, уже лежащие в холодном хранилище, остаются на месте.

## Из командной строки

```bash
flare retention show
flare retention set logs --days 30
flare retention set logs --days 30 --cold-after 7
flare retention set logs --days 30 --rule deployment.environment=dev:7 --rule k8s.namespace=load-test:1
flare retention set logs --clear-rules
```

`show` печатает действующий TTL каждого сигнала, перенос, правила и статус последнего изменения. `set` ждёт, пока ClickHouse применит изменение (`--no-wait` возвращается, как только API приняло запрос). Пропущенные параметры сохраняют текущее значение, поэтому один `--days 14` не сбрасывает правила. `--rule` принимает `ATTRIBUTE=VALUE:DAYS`, повторяется и заменяет существующие правила.

## Ограничения

- Срок - от 0 (вечно) до 18250 дней (50 лет).
- Второе изменение отклоняется с `409`, пока идёт применение. Изменение, которое не завершилось за 30 минут, например из-за перезапуска API, считается неудавшимся.
- API: `GET /api/retention` и `PUT /api/retention`. Устройство описано в [ADR-0143](../../docs-internal/adr/0143-retention-ttl.md) (TTL), [ADR-0144](../../docs-internal/adr/0144-cold-storage-rustfs.md) (холодное хранилище) и [ADR-0145](../../docs-internal/adr/0145-per-resource-retention.md) (правила по ресурсам).
